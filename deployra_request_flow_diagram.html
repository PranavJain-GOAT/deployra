📚 What Does Everything Actually Do? (Plain English)

Every box in the diagram explained as if you're explaining it to someone who has never coded

🌐 Request Initiation — Browser & Frontend
1
👤 User / Browser
Chrome / Firefox
clicks a button or link
This is you — sitting in front of the browser. You click "Buy Now" or "Login" or navigate to a page. That single click is what starts the entire chain of events described in this diagram. Nothing happens until you do something. Think of it like pressing the button on a vending machine — everything else is the machine doing its job after you press.
2
⚡ React 18 + Vite (Vercel CDN)
Frontend SPA • React Router
TanStack Query • Tailwind
React is the visual layer — the buttons, forms, cards, charts you see on screen. It's a JavaScript app that runs entirely in your browser. When you click something, React decides "I need to fetch some data from the server" and it hands that job off to TanStack Query (which is like a smart postman that also remembers the last letter it delivered, so it doesn't re-fetch unnecessarily). The whole frontend is hosted on Vercel's CDN, meaning it loads from a server nearest to you geographically — so it's fast.
You click→ React event fires→ TanStack Query calls useMutation/useQuery→ Axios makes the HTTP request
3
📡 Axios (withCredentials)
HTTP Client
withCredentials: true
Axios is the delivery person on the frontend. When React says "go get this data", Axios packages up the request (URL, method like GET/POST, and any data you typed in the form) and sends it to the backend server over the internet. The key setting here is withCredentials: true — this tells the browser "when you send this request, also attach any cookies you have stored for this site". Without this, the login cookie would never be sent and the server wouldn't know who you are. Axios also has an interceptor: if the server says "401 Unauthorized" (login expired), Axios automatically goes and gets a new login token and retries the original request — without you ever noticing.
React says "fetch data"→ Axios packages: URL + method + body→ Browser adds cookie header automatically→ Request flies to Render server
4
🍪 HttpOnly Cookie
accessToken (15min JWT)
refreshToken (7day JWT)
HttpOnly • Secure • SameSite
Think of this like a sealed government ID badge that the server gives you when you log in. It's stored in your browser, but with a special lock: HttpOnly means no JavaScript can read it — not even your own React app. Why? Because if a hacker somehow injects malicious code into the page (an XSS attack), they still can't steal your login token because JS literally cannot access it. The browser is the only one that can read it, and it automatically attaches it to every request. Secure means it only travels over HTTPS (encrypted). SameSite=Strict means it won't be sent on requests triggered by other websites (prevents CSRF attacks). There are TWO cookies: a short-lived accessToken (15 mins, used for every request) and a long-lived refreshToken (7 days, only used to silently get a new accessToken when the short one expires).
Server sends Set-Cookie header on login→ Browser stores cookie securely→ Every future request: browser auto-attaches it→ Server reads it to know who you are
☁️ Network & Infrastructure
5
🛡️ Render Load Balancer
Reverse Proxy
HTTPS Termination
X-Forwarded-For header
This is the front door security guard of the building. When your request arrives at Render's servers, it first hits this Load Balancer. It does two important things: (1) It handles all the HTTPS encryption — it decrypts the incoming request (so the Node.js app doesn't have to deal with SSL certificates), and re-encrypts the response before sending it back. (2) It adds a special header called X-Forwarded-For which contains YOUR real IP address. This is critical because our rate-limiter needs to know your actual IP to enforce "max 8 login attempts per IP". Without this, the rate-limiter would see Render's own internal IP and think everyone is the same person.
6
⚙️ Express 5 / Node.js (app.js)
app.set('trust proxy', 1)
Entry point for all requests
src/server.js
This is the main office building. Every single request — login, buy product, upload image, get notifications — enters through here. The first thing it does is app.set('trust proxy', 1) which tells Express: "Hey, we're behind a load balancer, trust the X-Forwarded-For header to get the real user IP". Without this, all rate limiting would be broken. From here, the request travels through a series of "middleware" — think of it as going through different departments in an office before reaching the person who can actually help you.
🛠️ Middleware Chain — Every request passes through ALL of these
7
🪖 Helmet
15 HTTP security headers
X-Frame-Options, HSTS
CSP, X-Content-Type-Options
Helmet is like the security checklist at the entrance of a building. It doesn't look at who you are — it just adds a bunch of protective rules to every single response the server sends back. For example: X-Frame-Options: DENY prevents hackers from embedding your site inside a hidden iframe and tricking users into clicking things (clickjacking). Strict-Transport-Security tells the browser "only ever visit this site over HTTPS, never plain HTTP". Content-Security-Policy tells the browser "only load scripts and images from trusted sources, not random URLs". It's essentially slapping a bunch of safety stickers on every outgoing response.
8
🌍 CORS
Origin whitelist
credentials: true
Blocks all unlisted origins
CORS stands for Cross-Origin Resource Sharing. Think of it as a guest list at a club. By default, browsers block requests from one website (like deployra.vercel.app) to another server (like our Render backend). CORS is how the backend says "it's okay, I allow requests from these specific addresses". We whitelist: deployra.vercel.app and localhost:5173 (for development). Anyone else trying to send requests to our API gets blocked instantly. The credentials: true part specifically tells the browser "yes, you are allowed to send cookies in these cross-origin requests" — without this, the HttpOnly cookies would be stripped before reaching the server.
9
🍪 Cookie Parser
Parses Cookie: header
Populates req.cookies
req.cookies.accessToken
When the browser sends a request, cookies are sent as a single long text string in the header, like: Cookie: accessToken=abc123; refreshToken=xyz789; theme=dark. The Cookie Parser's job is to split that string apart and turn it into a nice JavaScript object so the code can easily do req.cookies.accessToken instead of manually splitting strings. It's like taking a receipt with everything on one line and organizing it into neat columns in a spreadsheet. This is a custom inline middleware — no external library needed, just a few lines of string splitting.
"Cookie: accessToken=abc; theme=dark"→ Cookie Parser splits it→ req.cookies = { accessToken: 'abc', theme: 'dark' }
10
📦 Body Parsers
express.json()
express.urlencoded()
Populates req.body
When you submit a form (like a login form with email and password), that data is sent in the body of the HTTP request as a raw text string, like: "email=pranav@gmail.com&password=secret123". Body Parsers convert that raw text into a real JavaScript object so the controller can do req.body.email and req.body.password. express.json() handles API calls sent as JSON (most calls). express.urlencoded() handles old-school HTML form submissions and OAuth callbacks. Without this, req.body would just be undefined and nothing would work.
Raw: "email=a@b.com&password=abc"→ Body Parser processes it→ req.body = { email: 'a@b.com', password: 'abc' }
🔒 Security, Routing & Authentication
12
⏱️ Rate Limiter
8 login attempts / 15min / IP
429 on breach
Winston logs IP + email
Imagine a bank that only lets you swipe your card 8 times in 15 minutes. If you exceed that, the machine blocks you. That's exactly what this does. It tracks your IP address and counts how many login attempts you've made. If a hacker is trying thousands of password combinations (brute force attack), they get blocked after 8 tries. Each limit is different by route: login gets 8 tries, password reset gets 5 per hour, email resend gets 3 per hour. When blocked, the server returns HTTP 429 "Too Many Requests" and our logger writes a warning with the IP address and email they were trying to access.
13
🛣️ Express Router /api/v1/*
9 route files
Matches method + path
routes/index.js
The Router is like the receptionist at the front desk. When a request comes in, it looks at the URL and HTTP method (GET, POST, etc.) and directs it to the right department. "POST /api/v1/auth/login? That goes to the auth team." "GET /api/v1/products? That goes to the product team." There are 9 separate route files (auth, products, users, payment, uploads, admin, purchases, orders, notifications) each handling their own set of endpoints. The router just reads the address and forwards the request to the right place.
14
✅ Joi Schema Validation
registerSchema: name, email, password
400 Bad Request if invalid
Runs before controller
Before we even let the controller touch the data, Joi acts like a form validator at the post office — it checks whether what you sent is actually valid. Is the email a real email format? Is the password at least 8 characters? Is the role either "CLIENT" or "DEVELOPER"? If any of these checks fail, Joi immediately rejects the request with a HTTP 400 Bad Request and tells you exactly which field is wrong — e.g. "password must be at least 8 characters". The controller never even runs. This is the first line of defense against garbage data.
15
🔑 authenticate Middleware
jwt.verify(token, JWT_SECRET)
prisma.user.findUnique
401 Unauthorized if fails
This is the ID badge scanner at the entrance of a secure floor. It reads your accessToken cookie (which the browser auto-sent with the request), and calls jwt.verify() to check: (1) Is this token genuinely signed by our server? (2) Has it expired (after 15 minutes)? If valid, it decodes the token to extract your userId and role, then does a quick database lookup to confirm you still exist (accounts can be deleted). It then attaches req.user = yourUserObject so every subsequent middleware and controller knows exactly who is making the request — no database lookup needed again. If the token is missing or expired or fake, it returns HTTP 401 Unauthorized immediately.
Read accessToken from cookie→ jwt.verify() checks signature + expiry→ Prisma confirms user exists in DB→ req.user = user → next()
16
🛡️ authorize / adminOnly (RBAC)
req.user.role check
CLIENT / DEVELOPER / ADMIN
403 Forbidden if wrong role
authenticate confirmed who you are. authorize checks what you're allowed to do. Think of it like different security clearance levels in a company. A regular user (CLIENT) cannot access the admin dashboard. A developer can upload products but not approve them. Only an admin can approve, reject or suspend products. If you try to hit an admin endpoint as a regular user, even though you're logged in, you get HTTP 403 Forbidden. The role is stored in the JWT token itself (encoded at login time), so no extra DB call is needed — the middleware just reads req.user.role.
🎮 Controllers — Where the actual work happens
17
🔐 auth.controller.js
register, login, refresh
logout, Google OAuth
password reset, email verify
This is the registration and security desk. When you register, it takes your password and runs it through bcrypt (a one-way scrambler) with 12 rounds of scrambling. The original password is never stored — only the scrambled version. When you log in, bcrypt scrambles what you typed and compares the scrambled versions. If they match — you're in. Then it creates two JWTs (access token and refresh token), stores a fingerprint (SHA-256 hash) of the refresh token in the database, sets both as HttpOnly cookies, and logs the login to the LoginHistory table for audit purposes.
18-22
🎮 Other Controllers
product, payment, upload
user, admin controllers
Each controller is the specialist department that handles its own domain. product.controller: manages creating, listing, reviewing products. payment.controller: talks to Razorpay to create an order, then verifies the payment signature using cryptography. upload.controller: takes your image file, holds it in memory (RAM), then streams it directly to Cloudinary cloud storage — it never saves to disk. user.controller: handles your profile, purchases, wishlist, 2FA setup. admin.controller: lets admins approve/reject products and creates audit log entries for every action. All controllers call Prisma to talk to the database.
🗄️ Data Layer — Prisma ORM + PostgreSQL
23
📦 Prisma ORM
Type-safe query builder
prisma.user.findUnique()
schema.prisma → SQL
Prisma is a translator between JavaScript and SQL. Normally, to get a user from a database, you'd write raw SQL: SELECT * FROM "User" WHERE email = $1. With Prisma, you just write prisma.user.findUnique({where:{email:'...'}})} and it writes the SQL for you. It also gives you type safety — if you try to save a string to a number field, it catches the error before it even hits the database. Prisma uses a single shared connection instance (singleton) so the app doesn't create thousands of DB connections and crash the database (a very common beginner mistake).
24
🐘 Neon PostgreSQL
12 tables • Serverless
DATABASE_URL connection
prisma migrate deploy
This is the actual filing cabinet where all data is permanently stored. Neon is a cloud-hosted PostgreSQL database — think of it like Google Sheets but much more powerful, structured, and secure. Every user account, every product listing, every purchase, every refresh token (stored as a SHA-256 hash for security), every notification — all 12 tables live here. It's "serverless" meaning it automatically scales up when there's load and scales down when idle, so you don't pay for idle compute. When Deployra deploys to Render, it runs prisma migrate deploy which applies any database schema changes automatically.
🌏 External Services & Integrations
25-30
🌏 External APIs
Cloudinary • AWS S3
Razorpay • Google OAuth
Nodemailer • Winston
Cloudinary: When you upload a product image, it goes into RAM (not disk), then gets streamed directly to Cloudinary's servers. Cloudinary auto-optimizes it (compresses, converts format) and gives back a permanent HTTPS URL that gets stored in the database.

Razorpay: Handles Indian payments. Our server tells Razorpay "create an order for ₹499", Razorpay gives an order_id, your browser shows the Razorpay payment popup, you pay, Razorpay tells us the payment_id. We then verify the signature using a secret HMAC-SHA256 code to confirm Razorpay actually sent this (not a fake confirmation).

Google OAuth: When you click "Login with Google", we redirect you to Google. Google asks you to authorize. Then Google sends our backend a secret code. We exchange that code for your Google profile (name, email, picture). We create or update your account in our DB, then issue our own JWT tokens (we never store Google's token).

Nodemailer: Sends emails via SMTP. Email verification uses a random 32-byte token (from Node's crypto module) that expires in 24 hours. Password reset tokens expire in 10 minutes.

Winston: Our logging system. Every important event (login, rate limit breach, error) is written to log files. Not just console.log — it writes to actual files that persist, so you can audit what happened days later.

❓ KEY QUESTIONS — ANSWERED IN PLAIN ENGLISH

When are the HttpOnly cookies created, and where do they go?
Cookies are created in the auth.controller.js on login. After bcrypt verifies your password, the controller calls jwt.sign() twice (one for access token, one for refresh). It then calls res.cookie('accessToken', token, {httpOnly:true, secure:true...}) which adds a Set-Cookie header to the HTTP response. The browser receives this response, reads the Set-Cookie header, and automatically stores the cookie. From that moment on, every single request that browser makes to our backend will automatically include those cookies in the request headers — no JavaScript code needed, the browser does it on its own. The refresh token's SHA-256 hash is also stored in the RefreshToken database table (so we can revoke it on logout).
When the response comes back from the controller, where does it go next?
The controller calls res.json({success:true, data:{...}}). Express serializes (converts) that JavaScript object into a JSON text string and puts it in the HTTP response body. It travels back through Render's load balancer (re-encrypted to HTTPS), across the internet, and arrives in the browser. Axios is the one that receives it on the frontend — it automatically parses the JSON text string back into a JavaScript object and puts it in response.data. Then TanStack Query takes that data, stores it in its cache, and React re-renders the UI with the new data. If it was a login response, the browser also processes the Set-Cookie headers before Axios even sees the response body.
Who converts the JSON string into a readable JavaScript object on the frontend?
Axios does this automatically. When a response comes back from the server with Content-Type: application/json, Axios calls JSON.parse() under the hood, which converts the raw JSON string '{"success":true,"data":{"id":"abc"}}' into an actual JavaScript object {success: true, data: {id: 'abc'}}. This is placed in response.data. TanStack Query then receives this already-parsed object and stores it in the query cache. You never have to call JSON.parse() yourself.
What happens when the access token expires (after 15 minutes)?
The server returns HTTP 401 Unauthorized. Axios has a response interceptor configured on the frontend. When it sees a 401, it automatically fires a POST /api/v1/auth/refresh request (the browser auto-sends the refreshToken cookie). The server reads the refreshToken cookie, hashes it with SHA-256, looks it up in the database, verifies it's not revoked or expired, then issues a new accessToken and sets a new Set-Cookie header. The original failed request is then retried automatically with the new token. You never see a logout screen — the entire thing happens silently in the background in milliseconds.
What happens when you log out?
The logout endpoint calls res.clearCookie('accessToken') and res.clearCookie('refreshToken') — this tells the browser to delete those cookies. Simultaneously, it does prisma.refreshToken.update({where:{id}, data:{revoked:true}}) which marks the refresh token in the database as revoked. So even if somehow someone had a copy of your refresh token, it would be rejected because the database says it's revoked. "Logout All Devices" does prisma.refreshToken.updateMany() which revokes all refresh tokens for your account simultaneously.
What is bcrypt doing with the password, and why can't we just read it back?
bcrypt is a one-way hashing function. It takes your password and scrambles it using a complex mathematical algorithm, 12 rounds deep, with a random "salt" (extra random data) mixed in. The result is a 60-character string that looks like garbage: $2b$12$abcdefghij.... There is mathematically no way to reverse this back to the original password — not even our own server can do it. When you log in, bcrypt scrambles what you just typed and compares the scrambled versions. If they match, the password was correct. This means even if someone steals our entire database, they cannot know any user's actual password.
How does image upload work? Does it save to the server's hard drive?
No, it never touches the hard drive. Multer is configured with memoryStorage() which means the uploaded file is held entirely in the server's RAM as a Buffer. Then we create a readable stream from that buffer and pipe it directly to Cloudinary's servers. Cloudinary stores it, optimizes it (auto quality, auto format), and returns a permanent HTTPS URL like https://res.cloudinary.com/deployra/products/abc123.webp. That URL gets saved to the database. When someone views the product, their browser loads the image directly from Cloudinary's CDN — not from our server at all.
