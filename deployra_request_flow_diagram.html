📚 What Does Everything Actually Do? (Plain English)

In the CORRECT order things happen — from click to response

🌐 Browser & Frontend
1
👤 User / Browser
Chrome / Firefox
clicks something
You are box 1. When you click "Login", you kick off the entire chain. Nothing happens without your action. Think of it as pressing the button on a vending machine — everything below is the machine doing its work after you press.
2
⚡ React 18 + Vite
Frontend UI
Vercel CDN
React is the visual layer — all the buttons, cards, forms you see. When you click something, React says "I need data from the server" and hands the job to TanStack Query, which then tells Axios to go fetch it. The whole frontend is a static bundle (HTML + JS files) sitting on Vercel's CDN servers around the world.
3
📡 Axios
withCredentials: true
sends the HTTP request
Axios is the delivery person — it packages the request (URL, method, data) and sends it to the backend. The withCredentials: true setting tells the browser: "when sending this request, also include any cookies you already have stored for this site". On your first login, there are no cookies yet, so nothing is attached. On return visits, the browser finds your stored accessToken cookie and adds it automatically. Axios also watches for 401 errors — if the server says your token expired, Axios silently gets a new one and retries. You never see a logout.
React says "send POST /login"→Axios packages: URL + method + body→Browser adds cookies if any exist→Request sent to Render server
☁️ Network & Infrastructure
4
🛡️ Render Load Balancer
Reverse Proxy
HTTPS Termination
X-Forwarded-For
This is the front door security guard of the building. It receives the encrypted HTTPS request, decrypts it (so the Node.js app doesn't have to handle SSL certificates), and adds your real IP address in an X-Forwarded-For header before forwarding it internally. This real IP is critical for rate limiting to work correctly.
5
⚙️ Express app.js
trust proxy: 1
Entry point
The main lobby of the office building. Every request enters here. The first config it runs is app.set('trust proxy', 1) — this tells Express to trust that the X-Forwarded-For header from Render's load balancer is genuine. Without this, Express would ignore it and the rate limiter would see Render's internal server IP for everyone, effectively disabling IP-based rate limiting entirely.
🛠️ Middleware Chain (every request goes through all of these)
6
🪖 Helmet
15 security headers
slapped on every response
Helmet is like a checklist of safety stickers that gets stuck on every outgoing response. It doesn't care about who you are or what you're asking for — it just adds protection rules. X-Frame-Options:DENY prevents your site from being embedded inside an invisible iframe used for clickjacking attacks. Strict-Transport-Security forces the browser to always use HTTPS. Content-Security-Policy tells the browser only load scripts from trusted sources.
7
🌍 CORS
Guest list for the API
blocks unlisted origins
CORS is the guest list at the club door. By default, browsers block websites from calling APIs on other domains. CORS is the server's way of saying "it's okay, these specific websites are allowed". We allow deployra.vercel.app and localhost:5173. Any other website trying to use our API gets blocked. The credentials:true part specifically allows cookies to be sent along with cross-origin requests — without it, the login cookie would be stripped off before reaching the server.
8
🍪 Cookie Parser
READS cookies
does NOT create them
The browser sends cookies as one long messy string: Cookie: accessToken=abc123; theme=dark; refreshToken=xyz. Cookie Parser takes that messy string and splits it into a clean JavaScript object so code can easily do req.cookies.accessToken instead of manually splitting strings. Important: this middleware only READS cookies. It does NOT create them. Cookies are created much later by auth.controller in the response. On a first-time login visit, there are no cookies, so req.cookies is just an empty object.
"Cookie: accessToken=abc; theme=dark"→Cookie Parser splits string→req.cookies = { accessToken:'abc', theme:'dark' }
9
📦 Body Parsers
express.json()
express.urlencoded()
When you submit a form (login, register), the data arrives as a raw text string in the request body. Body Parsers convert it into a usable JavaScript object. express.json() handles API calls (most calls). express.urlencoded() handles HTML form submissions and OAuth callbacks. Without this, req.body would be undefined and no data would be accessible.
Raw body: '{"email":"a@b.com"}'→express.json() parses it→req.body = { email: 'a@b.com' }
🔒 Security, Routing & Authentication
10
⏱️ Rate Limiter
8 login tries / 15min
HTTP 429 on breach
Like a bank ATM that blocks you after too many wrong PIN tries. It tracks your IP address and counts how many times you've hit login or register. If you exceed 8 times in 15 minutes, the server blocks you and returns HTTP 429. This prevents hackers from trying thousands of password combinations automatically. Each endpoint has its own limit: password reset gets only 5 tries per hour, email resend gets 3 per hour.

🛣️ Express Router
9 route files
matches URL to handler
The receptionist who directs you to the right department. POST /api/v1/auth/login? Goes to auth team. GET /api/v1/products? Goes to product team. It reads the HTTP method and URL and figures out which controller function should handle it. There are 9 separate route files for different domains of the app.
12
✅ Joi Validation
schema validation

Before the actual work begins, Joi acts like a form validator at the post office. Is the email a real email format? Is the password at least 8 characters? Is the role one of the allowed values? If any check fails, it immediately rejects the request and tells you exactly which field is wrong. The controller never even runs. This prevents garbage data from ever reaching the database.
13
🔑 authenticate
reads req.cookies.accessToken
jwt.verify() checks it
HTTP 401 if invalid
This is the ID badge scanner at a secure floor. It reads the accessToken from req.cookies (which Cookie Parser put there in step 8). It calls jwt.verify() to check: is this token genuinely signed by our server? Has it expired? If valid, it decodes the token to get your userId and role, then quickly checks the database to confirm your account still exists. It sets req.user = your account so everything downstream knows who you are. This only runs on protected routes — /login and /register don't need it. If invalid or missing: 401 immediately.

14
🛡️ authorize (RBAC)
checks req.user.role
HTTP 403 if wrong role
Authenticate confirmed who you are. Authorize checks what you're allowed to do. Like security clearance levels in a company. A CLIENT can browse and buy. A DEVELOPER can create products. Only an ADMIN can approve or reject products. If you try to access an admin endpoint as a regular user, even though you're logged in, you get 403 Forbidden. The role is already in the JWT token so no extra database call is needed.
🎮 Controllers — where the actual work happens
15
🔐 auth.controller
WHERE cookies are created
login / register / OAuth
This is the security and registration desk. On register: your password gets bcrypt-hashed (one-way scrambled, 12 rounds — can never be reversed) and stored. Never the plain password. On login: bcrypt compares your typed password against the stored scramble. This is the exact moment HttpOnly cookies come into existence for the first time. The controller then sends res.json({success: true, user: {...}}) as the response body.

🍪 HttpOnly Cookie Created
BORN HERE in response
Set-Cookie header
This is the answer to your question about where cookies come from. The cookie is not at the start of the request chain — it comes into existence RIGHT HERE, in the HTTP response from auth.controller after a successful login. res.cookie('accessToken', jwtString, {httpOnly:true, secure:true, sameSite:'strict'}) adds a Set-Cookie header to the outgoing response. The response goes back through Render's load balancer, gets re-encrypted to HTTPS, and arrives at the browser. The browser processes the Set-Cookie header first (before React/Axios even sees the response body) and stores the cookies in its secure cookie jar. From now on, every single request from this browser to our backend will automatically include these cookies — no code needed, the browser handles it.

JSON.parse() automatic

Who converts JSON string to readable JavaScript object? Axios does it automatically. It calls JSON.parse() on the response body, turning the raw string '{"success":true,"data":{"id":"abc"}}' into a real JavaScript object {success:true, data:{id:'abc'}} available at response.data. You never call JSON.parse() yourself. TanStack Query takes that object, stores it in its cache (so it doesn't re-fetch unnecessarily), and React gets notified of new data and re-renders the UI. React Hot Toast shows the success or error message.

❓ Key Questions Answered in Plain English

Why was HttpOnly Cookie in the wrong place before?
Because on a first-time login, there is no cookie yet. The cookie doesn't exist until auth.controller successfully verifies your password, creates JWTs, and calls res.cookie() in the login RESPONSE. Only after that response reaches the browser does the cookie come into existence. On subsequent requests, the browser auto-attaches the stored cookie — which is what Axios's withCredentials:true enables. Cookie Parser (middleware step 8) just reads existing cookies if they're there. So the correct order is: login request goes in with no cookie → auth.controller creates it → it comes back in the response → browser stores it → all future requests auto-send it.
When the access token expires (15 mins), what happens?
The server returns HTTP 401 Unauthorized. Axios has a response interceptor that catches 401 silently. It automatically fires a POST /api/v1/auth/refresh request. The browser sends the refreshToken cookie (which has a 7-day life). The server reads it, does sha256(cookie) and looks it up in the RefreshToken DB table to confirm it's valid and not revoked. If valid, it issues a new accessToken via res.cookie() and the original failed request is retried automatically. You never see a logout screen. The whole thing happens in milliseconds, invisibly.
What happens when you log out?
auth.controller calls res.clearCookie('accessToken') and res.clearCookie('refreshToken') — the browser deletes both cookies. Simultaneously, it runs prisma.refreshToken.update({where:{id}, data:{revoked:true}}) which marks the DB entry as revoked. So even if someone somehow copied your refresh token, it would be rejected because the database says it's revoked. "Logout All Devices" runs prisma.refreshToken.updateMany() which revokes all sessions at once.
Where is bcrypt used and why can't the password be recovered?
bcrypt is used in auth.controller on register and password-change. It's a one-way hashing function. bcrypt.hash('yourPassword', 12) produces a 60-character string that looks like garbage. There is no mathematical way to reverse it. On login, bcrypt.compare('whatYouTyped', 'storedHash') scrambles what you typed and checks if the scrambled versions match. Even if someone steals the entire database, they cannot recover any user's actual password. The cost factor of 12 means ~250ms per hash — slow enough to make GPU brute-forcing impractical.
Does image upload save to the server's hard drive?
No, never. Multer is configured with memoryStorage() so the uploaded file lives entirely in the server's RAM as a Buffer. Then a readable stream is created from that buffer and piped directly to Cloudinary's servers. Cloudinary stores, optimizes, and serves the image from their CDN. Cloudinary returns a permanent HTTPS URL like https://res.cloudinary.com/deployra/products/abc.webp. That URL gets saved to the Product table in the database. When users load the product page, their browser fetches the image directly from Cloudinary's CDN — not from our server at all.
